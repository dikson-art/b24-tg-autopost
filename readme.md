# b24-tg-autopost — автопостинг «Вопросы с лекций» (Битрикс24 → Telegram)

Публикует короткие видео из папки «Вопросы с лекций» (Диск Битрикс24, портал artera.bitrix24.ru)
в Telegram-канал: видео + подпись (вопрос/лектор) + ссылка на страницу лекции на medinfoservice.org.

**Работает полностью в GitHub Actions** — регулярно (в среднем 5–6 постов в день), без зависимости
от каких-либо компьютеров или серверов. Публикует в боевой канал **@doctor_lecture** («Доктор, вам лекция»).

- Расписание: попытки запуска каждый час в течение дня (10:15–21:15 МСК); в workflow встроена «защита темпа» — пост не чаще, чем раз в ~75 минут, поэтому реальный ритм ≈ 1 пост в 1.5–2 часа.
- Workflow: `.github/workflows/b24-autopost.yml` (есть и ручной запуск: Actions → Run workflow).

## Состав

| Что | Где |
|---|---|
| Сервис (скачивает из Б24, сжимает при необходимости, постит в Telegram) | `tools/b24-autopost/service.py` |
| Шаблон конфига (секреты подставляются из GitHub Secrets) | `tools/b24-autopost/config.example.json` |
| Журнал публикаций (защита от дублей) | `tools/b24-autopost/state.json` — обновляется и коммитится автоматически |
| Зависимости от платежей (что оплачивать и где следить) | `docs/PAYMENTS.md` |

## Секреты (Settings → Secrets and variables → Actions)

- `B24_WEBHOOK_URL` — входящий вебхук Битрикс24 (право «Диск»).
- `TG_BOT_TOKEN` — токен Telegram-бота, который публикует в канал.

Канал: **@doctor_lecture** (задан в workflow).

## Управление

- **Пауза автосерии:** Actions → «B24 Telegram autopost» → ⋯ → *Disable workflow*.
- **Ручной пост:** Actions → «B24 Telegram autopost» → *Run workflow*.
- **Логи:** вкладка run → шаги; на ошибках также сохраняется артефакт `logs-*`.

## Как это работает

1. Workflow собирает `config.json` из секретов.
2. `service.py --check` проверяет доступы (Битрикс24 + Telegram + канал).
3. `service.py --max-posts 1` берёт следующий неопубликованный клип:
   скачивает из Битрикс24 → при размере >49 МБ сжимает (ffmpeg) до ~46 МБ →
   сопоставляет со страницей лекции → публикует в Telegram.
4. До вызова Telegram в удалённой `main` сохраняется запись `pending` с уникальным `attempt_id`.
   Только после успешного сохранения начинается отправка. Подтверждённый ответ Telegram
   сохраняется как `published` с `message_id`. Сохранение повторяется до 5 раз, каждый раз
   поверх актуальной `main`, объединяя записи и сохраняя изменения других файлов.
   Force push не используется. `concurrency` исключает параллельные запуски этого workflow.

## Незавершённая отправка и восстановление

Если остаётся `pending`, сервис останавливает публикации. Ни ручной запуск, ни `force`
не снимают эту блокировку. Она нужна при сбое runner, неопределённом ответе Telegram
или невозможности сохранить подтверждение публикации. Автоматического повторения нет:
защита от дубля важнее непрерывности серии. Telegram и Git не образуют общую транзакцию,
поэтому гарантировать одновременно доставку и отсутствие дублей при любом сбое нельзя.

1. Не перезапускайте рабочий автопостинг для проверки.
2. Сверьте конкретный клип с каналом и журналом запуска; при ошибке доступен артефакт
   `logs-<run_id>` с журналом и локальным `state.json` (без config и секретов).
3. Если публикация подтверждена, замените только эту запись `pending` на `published`,
   сохраните `attempt_id`, укажите проверенный `message_id` и время публикации.
4. Удаляйте reservation для повторной отправки только после подтверждения, что видео
   не опубликовано и исходный запуск завершён. При неизвестном результате оставьте блокировку.

В GitHub Actions обязателен `B24TG_DURABLE_STATE=1` (задан workflow). Локальный режим
сохраняет состояние на диск; он не обеспечивает общий журнал с Actions. Резервный
локальный планировщик должен оставаться выключенным. Ручное удаление записей, откат
`state.json` или обход сервиса могут нарушить защиту.

Ошибки сохранения/сверки состояния возвращают код 3 и `failure_kind=state`.
Ошибки этапа публикации и подготовки описываются отдельно; сбой workflow не означает,
что Telegram ничего не получил. Незавершённые записи не считаются подтверждённой публикацией.

## Проверка без публикаций

`python3 -m unittest discover -s tests -v` — локальные Git-репозитории, реальные конфликты
push и подменённые вызовы Bitrix, сайта и Telegram. Сетевые обращения в тестах сервиса
запрещены. Отдельный PR workflow выполняет только эти тесты, без секретов и отправки.
`--dry-run` также не изменяет состояние, но обращается к Bitrix/сайту.
